## What was built

orbit now writes decision records only while a setting that reads them is on: a granted chain key, a sign-off setting of change or program, or a tripwire set to halt. A new command, orbit decisions status, says whether records are written and which settings read them. Each workflow skill's body now carries only the basic content of the decision-writing rule: run that command at each command's first step and again after the session edits the project config, and follow the rule when it says records are written. The rule itself moved, every clause kept but its opening one, into the reference file each skill ships. The skill bodies are about 34,000 characters smaller, and the budget test's ceilings were lowered to match.

## New terms

- **decision record**: A small file the AI writes when it makes a call in one of eighteen listed areas, or before it stops to ask at one of five listed situations, with the answer recorded beside it. (defined in ledger-2026-11-18T15-16-25Z.json, ledger-2026-11-18T16-38-57Z.json, ledger-2026-11-18T16-43-21Z.json, ledger-2026-11-18T23-54-52Z.json, ledger-2026-11-19T00-05-57Z.json, ledger-2026-11-19T15-58-32Z.json)
- **orbit decisions status**: an orbit command that reads the project settings and says whether decision records are written, and which settings read them (defined in account-2026-11-19T17-08-49Z.json)
- **stop**: A record that the AI needed the user at a moment, holding the question put to them; it stays open until a record of the answer names it. (defined in ledger-2026-11-19T15-58-32Z.json)
- **trail**: a change's folder of run records, where its decision records are kept (defined in account-2026-11-19T17-08-49Z.json)
- **tripwire**: A check orbit runs on a change that either notes what it finds or, when set to halt, stops the work until the user answers. (defined in ledger-2026-11-18T15-16-25Z.json)

## New seams

No new question is asked. One setting-dependent behaviour is new: with none of the three reading settings on, the AI writes no new ledger entry or stop record, and with any of them on it writes them as before. Whatever the settings, an answer to a stop already in a change's history, or a fix of a record already there, is still written.

## The ledger

### ledger-2026-11-18T15-16-25Z.json

- Area: defaults
- Decided: Decision records are written only while something that reads them is switched on: a command allowed to run the next step by itself, a sign-off setting of change or program, or a tripwire set to halt. A chaining setting that allows no command, and tripwires left to only note what they find, the default, do not count.
- Alternatives considered:
  - count a setting as on whenever it is written in the settings file at all
  - leave the tripwires out of the list
- Why: Each of the three is counted in exactly the state where it reads the records; in the other states nothing reads them, and writing them would keep the cost the ruling removes.
- Relies on:
  - ruling R-rop-17 of `reduce-orbit-phase1`

### ledger-2026-11-18T16-38-57Z.json

- Area: things others build on
- Decided: A new orbit command, run the same way at the start of every session, answers whether decision records are to be written and names the settings that read them; it takes no change name, since the settings belong to the whole project.
- Alternatives considered:
  - add the answer to the status of one change
  - have the command that writes a record refuse when none is needed
- Why: Some sessions never ask for one change's status, and a refusing write command would still need the whole rule in every skill to know when to call it, so only a command of its own can replace the rule with one short line that is the same everywhere.
- Relies on:
  - ruling R-rop-4 of `reduce-orbit-phase1`
  - ruling R-rop-5 of `reduce-orbit-phase1`

### ledger-2026-11-18T16-43-21Z.json

- Area: defaults
- Decided: With every setting at its default, a decision record written anyway is still accepted and checked as today; orbit does not start refusing or warning about it.
- Alternatives considered:
  - refuse such a record
  - accept it and print a note that no setting reads it
- Why: Nothing depends on such records being absent, it costs one reader at review as any record does today, and refusing or warning would change what orbit does at the defaults beyond the one change the goals allow.
- Relies on:
  - goal RG0 of `reduce-orbit-phase1`
  - goal G0 of `automate-dev-flow`

### ledger-2026-11-18T23-54-52Z.json

- Area: docs
- Decided: Every place that says decision records are written under every setting is corrected in the same change: the command reference, the onboarding text, the project instructions of this repository and the requirements that state the rule; the new command that says whether records are written is documented beside the existing one that reads them.
- Alternatives considered:
  - leave the onboarding text as it is, since this program leaves that skill's own text alone
- Why: Each of those texts would otherwise state something no longer true once the change lands, and the onboarding line is a restatement of the rule rather than text of its own.
- Relies on:
  - ruling R-rop-17 of `reduce-orbit-phase1`

### ledger-2026-11-19T00-05-57Z.json

- Area: docs
- Decided: The settings page also tells the user, for each of the three settings that read decision records, which state of the setting makes the AI start writing them, beside the existing description of what the setting does.
- Alternatives considered:
  - leave the settings page as it is and say it only on the command reference page
- Why: A user turning a setting on reads the settings page, and the records it starts are a consequence of that choice they should see there.
- Relies on:
  - ruling R-rop-17 of `reduce-orbit-phase1`
  - explore decision D-rbs-5

### ledger-2026-11-19T15-58-32Z.json

- Area: defaults
- Decided: With every setting at its default, the AI writes no new decision record, but it still records the user's answer to a stop already in the change's history and still writes the corrected version of a record a review found unclear.
- Alternatives considered:
  - forbid every record at the defaults and name the gaps this leaves as limits
  - have the command also look at the change's history, so an existing record turns writing on
- Why: Records already in a history keep being read at the defaults, and a stop written while a setting was on must still be answerable after it is turned off; forbidding these would leave a stop unanswered or a record unfixable.
- Relies on:
  - ruling R-rop-17 of `reduce-orbit-phase1`
  - explore decision D-rbs-8

### ledger-2026-11-19T17-04-30Z.json

- Area: what the user sees or does
- Decided: The help text of the new command says: "Report whether decision records are written: true when a setting that reads them is on (writes nothing)", and the help of the decisions group now says it covers both whether records are written and the brief the reading step gives its reader.
- Alternatives considered:
  - reuse the one-line output as the help text
  - leave the decisions group help naming only the brief
- Why: The design fixed the command's output lines and its JSON form but not its help text; this wording names what the result means and that the command changes nothing, and the group's old help would no longer describe both of its commands.
- Relies on:
  - explore decision D-rbs-2

## Deviations from the charter

Two, both decided in the proposal review and walk (D-rbs-10): the charter says that at the defaults the AI writes no resolution, but a resolution answering a stop already in a trail, and a replacement fixing a record already there, are still written, so turning the last reading setting off strands no stop; and the charter says the review's reading step selects nothing at the defaults, which holds only on a trail with no records, since records written earlier are still read and fixed. The command reports write and readers rather than whether records are owed, because owed already means a record awaiting its reading.
