## What was built

Two blocks of the skill bodies that a session acts on once now wait in reference files until that moment. Eleven bodies (apply, archive, architect, review, verify, propose, address-reviews, ff, continue, new and audit-drift) keep when their run summary is written, the command that writes it and what they say in chat, plus one shared sentence telling the AI to read a new reference file, run-summary-emit.md, before the session's first run summary; what goes into the record moved there unchanged. Apply's account step, and the review walk's, became a line sending the AI to a reference file that holds the step whole and decides whether to write anything. The skill-body convention gained the rule for a block acted on once, and the budget test's ceilings came down to the new sizes plus 5%. The bodies went from 389,374 to 369,392 characters in all; apply's from 27,124 to 18,887. No workflow does anything differently.

## New terms

- **account**: the plain-language note a change carries of what it built, where the user is newly asked something, and where the work left its plan (defined in ledger-2026-11-17T19-38-39Z.json, ledger-2026-11-17T19-38-41Z.json)
- **account step**: the instruction to write the change's account, the plain record of what it built, its new seams and its deviations, once apply is complete (defined in account-2026-11-17T19-31-58Z.json)
- **apply gate**: orbit's check that a change's tasks are done; it reads passed when every task is checked, or only tasks handed to the user remain (defined in ledger-2026-11-17T19-38-39Z.json, ledger-2026-11-17T19-38-41Z.json)
- **conditional field**: a field of that record owed only when something happened earlier in the session, such as a decision to proceed past an unpassed review (defined in ledger-2026-11-17T19-38-43Z.json)
- **consent field**: the field of a session record that says whether the user typed the command, answered a prompt for it, or a setting allowed it (defined in ledger-2026-11-17T19-38-43Z.json)
- **drift check**: orbit's audit-drift command, which scans the project for records and documents that disagree (defined in ledger-2026-11-17T19-38-43Z.json)
- **reference file**: a file beside a skill's body that the agent reads only when the body tells it to (defined in ledger-2026-11-17T19-38-39Z.json, ledger-2026-11-17T19-38-41Z.json, ledger-2026-11-17T19-38-43Z.json)
- **review walk**: the address-reviews command, which resolves a review's findings one by one (defined in account-2026-11-17T19-31-58Z.json)
- **review walk**: the session that goes through a review's findings one by one and resolves each (defined in ledger-2026-11-17T19-38-39Z.json, ledger-2026-11-17T19-38-41Z.json)
- **run summary**: the record each orbit command writes at the end of its session, saying what it did and what comes next (defined in account-2026-11-17T19-31-58Z.json)
- **session record**: the JSON summary (the run summary) each orbit command writes about its session, through orbit emit (defined in ledger-2026-11-17T19-38-43Z.json)

## The ledger

### ledger-2026-11-17T19-38-39Z.json

- Area: when things go wrong
- Decided: Each account step keeps in its skill only when to read its reference file — at the end of an apply session, and at the end of a review walk — and reads it every time; the reference decides whether to write the account. Nothing in orbit reports a change whose apply is complete and which has no account.
- Alternatives considered:
  - read the reference only when the apply gate reads passed
  - read it when the gate reads passed or this session declares its remaining tasks as handoffs to the user
  - decide from the task list alone, in the skill's own text
- Why: The gate counts a task handed to the user only once a session's run summary has declared it, and that summary is written after the account step, so a gate-keyed read would miss a change that ends on its first such task; any condition that sees that case would sit in every apply and walk body, which stays loaded on every turn of every session, while one read at the step's moment costs only the session's last few turns.
- Relies on:
  - explore decision D-opsd-8
  - ruling R-rop-4 of `reduce-orbit-phase1`
  - goal RG0 of `reduce-orbit-phase1`

### ledger-2026-11-17T19-38-41Z.json

- Area: when things go wrong
- Decided: Once the account step's rules move to a reference file, the apply skill tells the agent to read them when the apply gate reads passed at the end of the session, and the review walk tells it to read its own after its logs, when the change is active and holds an account; nothing in orbit reports a change whose apply is complete but which has no account.
- Alternatives considered:
  - have orbit status report a missing account when apply is complete
  - leave the account step whole in the apply and walk bodies
- Why: The gate's passed state is exactly when the step applies, and orbit already reports it, so it picks the read with no change to the engine, which this stage leaves alone; a report of a missing account would guard against a skipped read, and is weighed at the evaluation if real sessions are seen to skip it.
- Relies on:

### ledger-2026-11-17T19-38-43Z.json

- Area: when things go wrong
- Decided: The detail of each session record (its fields, their shapes, and when each conditional field is owed) moves out of the skill bodies into a reference file that every session reads before writing its first session record; if a session skips that read, a conditional field it never learned of is left out and nothing reports the loss, except a missing consent field, which the drift check already flags.
- Alternatives considered:
  - keep in each body one line per conditional field saying when it is owed, and read the reference only when one is owed
  - keep those lines in apply's body only, and read the reference in every other skill
- Why: The read comes at the one moment every session reaches, where the agent needs the fields to write anything, so it asks for no judgement; the text keeps a single home instead of a second copy of its triggers that could drift; and the bodies shrink the most.

## Deviations from the charter

Three. The charter sends the record detail to each skill's existing run-summary schema reference; it went to a new, small run-summary-emit.md in each of the eleven skills instead, because review's, address-reviews' and archive's schema references run to 15,000 to 31,000 characters and every session would have read one whole before its first record. The charter keeps the triggers in the bodies; the rules for when an optional field of the record is owed (apply's and archive's judgement entries, archive's deferred validations, propose's and ff's PR attachment) moved to the reference with the rest of the detail, as Sal chose over keeping a second copy in each body. And the account step moved whole, its conditions included, not only its field rules, so that the body carries no condition: the AI reads the reference every time apply's session ends. The charter's check found that the apply gate cannot report a missing account without an engine change, so none was made; it is on the evaluation stage's list.

The archive records its warnings and accepted risks after this brief was rendered; they appear in the archived change's brief and the program brief.

The proposal's Size section declares no size limit breached.
