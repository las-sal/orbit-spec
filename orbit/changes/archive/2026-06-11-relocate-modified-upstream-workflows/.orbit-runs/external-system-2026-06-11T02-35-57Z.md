## CRITICAL

### Generated slash commands omit the relocated runtime behavior
**File**: src/core/templates/workflows/apply-change.ts:250
**Description**: The direct slash-command surface is generated from each `CommandTemplate.content`, not from the paired skill body, but the `apply`, `new`, `continue`, `ff`, and `verify` command templates contain no Orbit additions at all. A fresh all-workflow init confirmed those generated command files have no execution-discipline or run-summary instructions; `explore` and `propose` contain only summaries and still lack an actionable instruction to write their required emit, so seven of the eight emitting slash commands do not reliably implement `orbit-run-summary-emit`. This violates the proposal's skill+command relocation scope and means invoking the generated `/orbit:*` command can skip behavior present in the skill. Add an actionable thin Orbit block to every corresponding command template (and the non-emission note to `bulk-archive`), then test every generated skill/command pair rather than only skill bodies.

### New and continue derive the next artifact from the wrong status field
**File**: orbit/changes/relocate-modified-upstream-workflows/specs/orbit-run-summary-emit/spec.md:209
**Description**: The delta and continue template say to identify the next missing artifact from `applyRequires`, but that field is the terminal pre-apply requirement set, not the ready-artifact queue. In the default schema, a freshly scaffolded change reports `applyRequires: ["tasks"]` while `proposal` is the ready next artifact, so this logic recommends the wrong artifact. The new template also claims `artifacts_created: ["proposal"]` and says new may create additional artifacts, contradicting its upstream guardrail and this delta's scaffold-only requirement. Select the first `artifacts` entry with `status: "ready"` for the next-artifact reason, and make new's example/report reflect zero generated artifacts.

### Codex output is not mechanism-neutral
**File**: src/core/init.ts:541
**Description**: The proposal says `/orbit:` references are rewritten per tool and the shared bodies contain no Claude-only constructs, but skill transformation is applied only to OpenCode and Pi, while the Codex command adapter also emits bodies verbatim. Fresh Codex output retains `/orbit:*` references plus `AskUserQuestion`, `TodoWrite`, `Task tool`, and `Skill tool` instructions (archive is the clearest case), none of which is a mechanism-neutral Codex contract. Decide the intended Codex invocation surface, neutralize or transform the shared bodies accordingly, and add a generated Codex-surface test that rejects unsupported tool names and invocation syntax.
