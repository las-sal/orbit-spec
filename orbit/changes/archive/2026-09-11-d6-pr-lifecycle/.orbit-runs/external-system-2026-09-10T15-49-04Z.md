## CRITICAL

### Generation-input precondition triggers on worktree PRESENCE, so an uncommitted exploration skips the PR layer on the canonical consume-mode path
**File**: src/core/templates/workflows/pr-choreography.ts:79
**Description**: The reference reads: "When a consume-mode staging directory `orbit/explore/<change-name>/` is present in the worktree, verify the same path exists on the TARGET REF. If it does not, SKIP THE PR LAYER ENTIRELY". The rule keys on presence in the worktree, not on the path being TRACKED — yet the hazard the rule exists for (lines 84-86: "COMMITTED content present on your branch and absent from the base") only arises for tracked content. I verified against real git in a scratch repo: an UNTRACKED `orbit/explore/foo/` survives `git switch -c foo origin/main` intact (git only rewrites tracked paths), while a COMMITTED one is deleted. `/orbit:explore` never commits anything, so in the ordinary explore → propose session under `pr: per-proposal` the staging dir is untracked and absent on `<remote>/<default>` — a performing AI applying the rule literally SKIPS the PR layer on exactly the path `orbit-propose-modifications`' "Typed propose opens the draft silently" scenario promises. The transcription does the same (`test/integration/pr-lifecycle/phase1.ts:150` tests `repo.exists(stagingDir)`, worktree presence) and every harness case commits the exploration first (`phase1.test.ts:276-301`, `303-320`), so the untracked case — the default state — is untested. The delta requirement carries the same over-broad wording (`specs/orbit-propose-modifications/spec.md` lines 25-31), though its scenario correctly says "is committed". Fix: condition the skip on the staging path being TRACKED in HEAD (`git ls-files --error-unmatch orbit/explore/<name>` succeeds) AND absent-or-different on the target ref; an untracked staging dir must NOT trigger the skip. While there, cover the "tracked on both refs with different content" variant (the switch would silently revert it), which the exists-on-target test misses. Add the untracked case to the harness asserting `proceed` with the exploration intact, and align the requirement prose with its scenario.

### Stage-entry APPEND has no read-current-body step; `gh pr edit --body-file` REPLACES, so a literal performance wipes earlier stages' entries
**File**: src/core/templates/workflows/pr-choreography.ts:295
**Description**: Every mention of the program path says "append" (`:259-260`, `:273-277`), and the only concrete command given is the recovery form `gh pr edit --repo <owner>/<repo> <url> --body-file <path>` (`:295-298`) — which sets the whole body. Nothing instructs the AI to fetch the current body first (`gh pr view --repo <owner>/<repo> <url> --json body -q .body`), concatenate the new entry, and write the whole result. ### The attachment record (propose emit) is written AFTER the phase-3 push and rides no D6-guaranteed push until archive — a fresh checkout between seams silently loses the attachment and the PR is stranded draft
**File**: src/core/templates/workflows/pr-choreography.ts:177
**Description**: `pr_attachment` needs `url`, so the propose/ff emit (`orbit-propose/SKILL.md:299-305`, "at command completion") necessarily follows commit → push → `gh pr create`. That emit — the AUTHORITATIVE record the tail dereferences — therefore sits uncommitted in `orbit/changes/<name>/.orbit-runs/` after the seam, and the reference's enumerated commit scope (`:132-137`) cannot include it. The proposal narrows the window to "whatever the user pushes in between", but the consequence here is not visibility: if the worktree is discarded or the branch resumed from a fresh checkout (the "REMOTE-ONLY program branch resumed in a fresh checkout" case tasks 6.2c itself names), the tail finds a WHOLLY ABSENT attachment, which per `specs/orbit-archive-modifications/spec.md:103-113` TERMINATES the PR path — per-proposal PRs stay draft forever with no designed path back (the fallback query is deliberately not keyed on absence). Nothing in the reference or completion output tells the user the record is uncommitted. Fix, in order of preference: (a) a second commit+push at the propose seam carrying the emit (`git add orbit/changes/<name>/.orbit-runs/propose-<TS>.json && git commit && git push`) — still the propose seam, so the two-seams decision holds; or (b) at minimum a one-line completion note naming the uncommitted attachment record and the consequence, and a named v1 limit in the reference's "Recording the attachment" section.

### Design's mid-flight-adoption risk bullet is inaccurate for this repo: the program branch is named by doc stem, and `d-arc` is not `d-arc-arbitered-flow`
**File**: orbit/changes/d6-pr-lifecycle/design.md:174
**Description**: "Mid-flight adoption (this repo: `d-arc` is 5 stages deep, unpushed-PR) — covered by 'first configured touch' birth". Under D-d6-7 (`design.md:139-141`) and the reference (`pr-choreography.ts:91-92`) the program branch name is the architecture doc's filename stem — `d-arc-arbitered-flow` — while this repo's program branch is `d-arc`. ## SUGGESTION

### Surface the HEAD-mismatch observation at archive ENTRY, not only in the post-move tail
**File**: src/core/templates/workflows/pr-choreography.ts:251
**Description**: The HEAD check runs "BEFORE any staging" but AFTER sync, move, and emit have already landed in the wrong branch's worktree; the recovery then asks the user to carry uncommitted archive writes across a `git switch`. The check is read-only and the attachment is already resolved at entry for the consent preview (`orbit-archive-change/SKILL.md:140`). Observing `git branch --show-current` ≠ `pr_attachment.branch` there and telling the user BEFORE the archive writes (or naming it in the preview) costs nothing and removes the cross-branch carry. Keep the tail's check as the guard; add the early readout.

### Define "this change's own artifact commits" for per-proposal compatibility
**File**: src/core/templates/workflows/pr-choreography.ts:105
**Description**: Compatibility is "no commits beyond the resolved default branch other than this change's own artifact commits", with no test stated; the transcription guesses "commit subject contains the branch name" (`phase1.ts:137-141`), which a performing AI has no reason to replicate. State a path test: every commit in `<remote>/<default>..<branch>` touches only `orbit/changes/<change-name>/` (and `orbit/explore/<change-name>/` deletions) — mechanical, and the same discipline the enumerated commit scope already imposes.

### Propose's commit-scope prohibition on directory prefixes is stricter than the archive's, for the same kind of orbit-created directory
**File**: src/core/templates/workflows/pr-choreography.ts:132
**Description**: The archive tail grants a bounded exception for the moved archive dir (`:266-269`, "orbit NAMES and CREATES that directory in this same invocation"); `orbit/changes/<name>/` at propose meets the identical criterion, yet propose prohibits any prefix, so the AI must enumerate `proposal.md`, `design.md`, `tasks.md`, every `specs/*/spec.md`, `.openspec.yaml` (with the fingerprints stamped at Step "Base-fingerprint capture"), and the moved `.orbit-runs/*` — the last two are the ones most likely to be forgotten, and both matter later (metadata and the explore trail). Either state the symmetric exception or list the file set explicitly, `.openspec.yaml` and `.orbit-runs/` included.

### Step 5.8 echo is unspecified for the attached-but-positively-invalidated archive

## Notes

What I probed. I read the emitted `references/pr-choreography.md` and `references/pr-archive-tail.md` (byte-identical to the source consts — verified by diffing `dist` output against the generated files) plus the propose/ff/archive/bulk-archive/architect body pointers as a performing AI, stepping each of the four paths (per-proposal propose → archive; cited per-architecture adopt-or-open → append → arc-done readout; `never`/absent/inert; the degradation branches: no remote, no `gh`, dirty tree, refused switch, diverged tip, positive invalidation). I ran two real-git experiments in a scratch repo to settle the switch semantics the generation-input rule rests on. I re-ran the suite (1997 passing), `orbit validate --strict` (valid), `orbit fingerprint --check` (5/5 verified), and grepped `src/` for child-process use: the only git spawn is the read-only diff inspection in `src/core/parsers/apply-state.ts`; the only `gh` use is upstream's `feedback` command (`gh auth status`), unrelated to this capability — the zero-engine-git thesis holds. The rung-3 `pr` field, its test, the orientation delta, the invalidation bullet with mirrored axes, the config.yaml commentary, the dated Touchpoints-provenance sentence, the text-order step renumbering, and the bulk-archive source naming all landed as described; the Position paragraphs landed with the phase mislabel flagged above. Lenses (passes 4 and 5) are skips — `orbit/lenses/` does not exist.

Pattern behind the findings. The engine half is tight; every issue is in the outward half, and most share one shape: a rule is stated in terms of an observable (worktree presence, "append", "own artifact commits", `--repo`) whose operational meaning is left to the performer, and where I checked the literal reading against real git or real `gh` semantics the literal reading was the unsafe one. The single-session ruling makes step 6's remote-tip detection the load-bearing safety property for shared branches, so its absence from the transcription deserves attention out of proportion to its size. The per-architecture path in this repo specifically is worth a sober look before the dogfood, because the stem-vs-branch-name mismatch means the design's "mid-flight adoption" reassurance does not describe what phase 1 would actually do here.
